Visibilidade Reflete Escopo de Corretude

Por que “isso deveria ser public ou private?” é a pergunta errada

O debate de sempre

Toda equipe discute sobre visibilidade em algum momento, e o raciocínio geralmente se divide entre “esconda para que ninguém use errado” e “deixe public porque precisamos em todo lugar.” Os dois lados estão discutindo se confiamos em quem chama, mas confiança não é o eixo interessante. Existe uma pergunta diferente por baixo, e ela produz decisões de design melhores.

Três tentativas de resolver o mesmo problema mostram a diferença, duas erradas de formas diferentes e uma que acerta.

O cenário

Digamos que você está construindo um sistema que organiza coisas em pastas (como um sistema de arquivos, um workspace de projeto, ou uma base de conhecimento). Você precisa de duas coisas.

  • Um tipo Folder que guarda entries nomeadas e garante unicidade (duas entries não podem ter o mesmo nome).
  • Um FolderManager que é dono da árvore de pastas e dispara events quando entries são adicionadas, para que a UI atualize, índices de busca se atualizem, e o histórico de undo registre as mudanças.

Quem tem permissão de chamar o quê?

Uma nota rápida sobre visibilidade em Rust

O primeiro conjunto de exemplos usa Rust, então aqui vai um guia rápido dos seus modificadores de visibilidade (com equivalentes em outras linguagens).

  • pub significa acessível de qualquer lugar, como public em C# ou um símbolo exportado em TypeScript/JavaScript.
  • pub(crate) significa acessível em qualquer lugar dentro da mesma biblioteca (chamada de crate em Rust), como internal em C# ou acesso a nível de package em Go.
  • pub(super) significa acessível apenas dentro do módulo pai. Rust organiza código em uma árvore de módulos (similar a namespaces ou packages), e pub(super) limita o acesso a um nível acima nessa árvore. Não existe equivalente direto em C# ou TypeScript.
  • Sem modificador (apenas fn ou o nome de um campo) significa private para o módulo atual, como private em C# ou uma função não exportada em TypeScript.

O importante é o gradiente, onde pub é totalmente aberto, pub(super) é restrito a uma fronteira específica de módulo, e sem modificador é totalmente fechado. O princípio se aplica independentemente da linguagem que você usa; seções posteriores mostram o mesmo padrão em C# e TypeScript.

Tentativa 1. Tudo é public

Ruim. Dois caminhos para a mesma mutação

use std::collections::BTreeMap;

// Everything is public. The caller can insert entries
// through the manager OR directly on the folder.

pub struct Folder {
    pub name: String,
    pub entries: BTreeMap<String, Entry>,
}

impl Folder {
    pub fn insert_entry(&mut self, name: String, entry: Entry) -> Result<(), String> {
        if self.entries.contains_key(&name) {
            return Err(format!("duplicate name: {name}"));
        }
        self.entries.insert(name, entry);
        Ok(())
    }
}

pub struct FolderManager {
    pub folders: Vec<Folder>,
}

impl FolderManager {
    pub fn add_entry(&mut self, folder_id: usize, name: String, entry: Entry) -> Result<(), String> {
        self.folders[folder_id].insert_entry(name, entry)?;
        self.dispatch_event(EntryAdded { folder_id, entry });
        Ok(())
    }
}

Isso compila e até funciona, desde que todo caller passe por manager.add_entry(). Mas nada força isso, e um caller pode facilmente escrever:

// This succeeds. The folder's invariant is upheld (no duplicates).
// But no event is dispatched. The UI does not refresh.
// The search index is stale. The undo history has a gap.
manager.folders[folder_id].insert_entry(name, entry)?;

Ou pior ainda.

// This bypasses duplicate checking entirely.
manager.folders[folder_id].entries.insert(name, entry);

Agora existem três formas de adicionar uma entry, e duas delas são bugs esperando para acontecer. O caller pode passar pelo manager (correto), pelo método do folder (localmente válido mas perde events), ou diretamente pelo map (errado de todas as formas), e nada no código o guia para a forma correta.

Tentativa 2. Trancar tudo

A reação natural é esconder tudo, tornar tudo private ou internal, e expor apenas o manager.

Ruim. Superproteção que esconde o design

pub struct Folder {
    name: String,                       // private
    entries: BTreeMap<String, Entry>,   // private
}

impl Folder {
    // All methods are restricted, even reads.
    pub(crate) fn name(&self) -> &str { &self.name }
    pub(crate) fn get_entry(&self, name: &str) -> Option<&Entry> { self.entries.get(name) }
    pub(crate) fn insert_entry(&mut self, name: String, entry: Entry) -> Result<(), String> { /* ... */ }
    pub(crate) fn remove_entry(&mut self, name: &str) -> Option<Entry> { self.entries.remove(name) }
}

pub struct FolderManager {
    folders: Vec<Folder>,  // private
}

impl FolderManager {
    pub fn add_entry(&mut self, folder_id: usize, name: String, entry: Entry) -> Result<(), String> { /* ... */ }
    pub fn folder(&self, id: usize) -> &Folder { &self.folders[id] }
    // ... dozens of pass-through methods for every read operation
}

Isso resolve o problema dos “dois caminhos”, já que callers só podem passar pelo manager. Mas troca um problema por dois.

1. Indireção forçada

Esconder tudo força o manager a criar uma camada de pass-through para cada operação de leitura que poderia ser acessada diretamente. O caller não consegue acessar folder.get_entry(), então o manager precisa expor get_entry(folder_id, name), e o mesmo para listar entries, ler o nome do folder, e qualquer outra consulta inofensiva. Cada um desses métodos não adiciona lógica nem garante nenhuma invariante.

Camadas de pass-through se justificam quando adicionam comportamento em cada acesso (auditoria, caching, permissões), mas aqui o manager não acrescenta nada às leituras e o pass-through é puro overhead. Cada método desses é superfície de código para manter, indireção para o leitor rastrear, e acoplamento que força o pass-through a mudar toda vez que o tipo subjacente muda. A “segurança” de esconder tudo se torna um imposto de manutenção que se acumula a cada nova funcionalidade.

2. Sobrecarga cognitiva

Um leitor que abre Folder vê pub(crate) em cada método e não consegue dizer se get_entry é restrito porque chamá-lo diretamente é perigoso ou porque foi varrido por uma política genérica. Quando um método de leitura carrega o mesmo modificador de visibilidade de uma mutação que genuinamente precisa de supervisão, os modificadores perdem o sentido e se tornam ruído que o leitor aprende a ignorar.

Os dois custos vêm de tratar um domain object inteligente como se fosse dado burro. O folder garante suas próprias invariantes, e esconder seus métodos de leitura implica que ele não pode ser confiado. O design acaba obscurecido em vez de revelado.

Tentativa 3. Visibilidade corresponde ao escopo de corretude

A pergunta que importa é se essa operação é completamente correta aqui, ou apenas localmente válida.

  • get_entry(), name(), contains_entry() são leituras. Nenhuma invariante de sistema depende de quem lê, e elas são completamente corretas isoladamente. Torne-as public.
  • insert_entry(), remove_entry() são mutações. Elas mantêm a invariante do próprio folder (sem duplicatas), mas são contextualmente incompletas. O manager também precisa disparar events e manter a consistência da árvore, então elas só são completamente corretas quando chamadas pelo manager. Restrinja-as à fronteira onde o manager opera.

Bom. Visibilidade comunica onde a corretude mora

// folder.rs

use std::collections::BTreeMap;

pub struct Folder {
    name: String,
    entries: BTreeMap<String, Entry>,
}

impl Folder {
    // Reads are public. No system invariant at stake.
    // Any caller can safely read folder contents.
    pub fn name(&self) -> &str { &self.name }
    pub fn get_entry(&self, name: &str) -> Option<&Entry> { self.entries.get(name) }
    pub fn contains_entry(&self, name: &str) -> bool { self.entries.contains_key(name) }

    // Mutations are restricted to this module, where the
    // FolderManager lives. Calling insert_entry directly
    // upholds the folder's "no duplicate names" invariant,
    // but skips event dispatching, leaving the rest of
    // the system out of sync. The manager is the only
    // entry point where insertion is fully correct.
    pub(super) fn insert_entry(&mut self, name: String, entry: Entry) -> Result<(), String> {
        if self.entries.contains_key(&name) {
            return Err(format!("duplicate name: {name}"));
        }
        self.entries.insert(name, entry);
        Ok(())
    }

    pub(super) fn remove_entry(&mut self, name: &str) -> Option<Entry> {
        self.entries.remove(name)
    }
}
// folder_manager.rs

pub struct FolderManager {
    folders: Vec<Folder>,
}

impl FolderManager {
    pub fn add_entry(&mut self, folder_id: usize, name: String, entry: Entry) -> Result<(), String> {
        // Local invariant: the folder rejects duplicates.
        self.folders[folder_id].insert_entry(name, entry)?;
        // System invariant: listeners are notified.
        self.dispatch_event(EntryAdded { folder_id, entry });
        Ok(())
    }

    // No need for pass-through read methods.
    // Callers use folder.get_entry() directly.
    pub fn folder(&self, id: usize) -> &Folder { &self.folders[id] }
}

Um leitor que vê pub em get_entry e pub(super) em insert_entry sabe imediatamente que leituras são seguras em qualquer lugar mas mutações precisam do contexto do manager, e o comentário no método restrito explica exatamente qual invariante de sistema seria violada sem ele.

Um tipo pode ser localmente correto mas contextualmente incompleto.

O folder garante suas próprias invariantes perfeitamente, mas usar seus métodos de mutação corretamente requer contexto (disparo de events, consistência da árvore) que callers fora da fronteira do módulo não têm. A restrição de visibilidade guia o caller até o ponto de entrada onde a operação é completamente correta.

Se o folder emitisse domain events por conta própria e mantivesse a consistência da árvore sozinho, insert_entry seria completamente correto no nível do folder, e o princípio diria que ele deveria ser public. A pergunta (“essa operação é completamente correta aqui?”) continua a mesma, mas a resposta muda dependendo de onde a fronteira de corretude realmente está. Um design diferente move a fronteira, não o princípio.

“Make invalid states unrepresentable” é tipicamente discutido como um princípio a nível de tipo sobre projetar estruturas de dados para que combinações ilegais de valores não possam existir. Visibility-matches-scope-of-correctness é o mesmo princípio elevado ao nível de integração, a fronteira onde componentes interagem entre si. Um tipo bem projetado impede a construção de um valor impossível; visibilidade bem projetada impede a chamada de uma operação a partir de um contexto onde ela seria incompleta. As duas garantias acontecem em tempo de compilação, não em runtime.

O mesmo padrão em C#

O mesmo padrão aparece em todo lugar. Considere uma Order em um sistema de e-commerce em C#. A order sabe como adicionar um line item e rejeitar duplicatas.

Ruim. Tudo public, dois caminhos de mutação

// Order.cs

public class Order
{
    public List<OrderLine> Lines { get; } = new();

    public void AddLine(OrderLine line)
    {
        if (Lines.Any(l => l.ProductId == line.ProductId))
            throw new DuplicateLineException(line.ProductId);
        Lines.Add(line);
    }
}
// A caller can bypass AddLine entirely:
order.Lines.Add(line);  // no duplicate check, no events, no totals

Ruim. Tudo escondido, superproteção

public class Order
{
    private readonly List<OrderLine> _lines = new();

    // Even reads are internal — callers must go
    // through OrderService for everything.
    internal IReadOnlyList<OrderLine> Lines => _lines.AsReadOnly();
    internal void AddLine(OrderLine line) { ... }
}

// The OrderService becomes a bloated pass-through
// for every read operation on Order.

Bom. Visibilidade corresponde ao escopo de corretude

// Order.cs

public class Order
{
    private readonly List<OrderLine> _lines = new();

    // Reads are public — no system invariant at stake.
    public IReadOnlyList<OrderLine> Lines => _lines.AsReadOnly();

    // Mutation is internal because the OrderService must also
    // recalculate totals and publish domain events. Calling
    // AddLine directly produces a valid order with stale
    // totals and missing events.
    internal void AddLine(OrderLine line)
    {
        if (_lines.Any(l => l.ProductId == line.ProductId))
            throw new DuplicateLineException(line.ProductId);
        _lines.Add(line);
    }
}
// OrderService.cs

public class OrderService
{
    public void AddLineToOrder(Order order, OrderLine line)
    {
        order.AddLine(line);         // local invariant
        order.RecalculateTotals();   // system invariant
        _eventBus.Publish(new OrderLineAdded(order.Id, line));
    }
}

A Order garante “sem produtos duplicados” por conta própria. Mas AddLine só é completamente correta quando chamada pelo service, que lida com as obrigações que a order não conhece. A visibilidade diz exatamente isso.

E em TypeScript

TypeScript tem modificadores de visibilidade mais limitados, mas o princípio ainda se aplica através de fronteiras de módulo.

Ruim. Tudo exportado, dois caminhos de mutação

// index.ts — exports everything
export { Folder } from './folder';
export { FolderManager } from './folder-manager';
// some-caller.ts — which one should I use?
manager.addEntry(folderId, entry);  // correct
folder.addEntry(name, entry);       // locally valid, events skipped

Bom. Fronteira de módulo controla o escopo de corretude

// folder.ts

export class Folder {
  private entries = new Map<string, Entry>();

  // Not part of the module's public API.
  // Consumers use FolderManager.addEntry(), which also
  // handles event dispatching and tree consistency.
  addEntry(name: string, entry: Entry): void {
    if (this.entries.has(name))
      throw new DuplicateNameError(name);
    this.entries.set(name, entry);
  }

  // Reads are part of the public API.
  getEntry(name: string): Entry | undefined {
    return this.entries.get(name);
  }
}
// index.ts (barrel file) — the module boundary.
// FolderManager is the entry point for mutations.
// Folder is available as a type for reading only.

export { FolderManager } from './folder-manager';
export type { Folder } from './folder';

A linguagem oferece menos ferramentas, mas o princípio é o mesmo, e o caller deve alcançar o ponto de entrada onde a operação é completa, não o ponto de entrada onde ela meramente não lança exceção.

Sempre explique o “porquê”

Os exemplos ruins também nunca explicam por quê a visibilidade é como é. Quando tudo é public não há nada para explicar, e quando tudo está escondido a explicação é apenas “política.” Nenhum dos dois comunica o design. Quando a visibilidade corresponde ao escopo de corretude, os métodos restritos se tornam os interessantes, porque marcam onde corretude local diverge de corretude contextual. O comentário em cada método restrito deve explicar qual invariante de sistema seria violada se ele fosse public, e se você não consegue escrever esse comentário, a restrição é superproteção e deve ser removida.

Uma hierarquia de ideias que se sustentam

Ela se apoia em alguns princípios.

  1. Tipos são donos de suas invariantes. Campos são private, métodos garantem as regras, e o tipo é localmente correto por construção. Se o tipo não garante suas próprias regras, não há nada sobre o que a visibilidade possa construir.
  2. Uma única forma de fazer qualquer coisa. Se dois caminhos levam ao mesmo resultado, elimine um. Tornar um método public quando um coordinator precisa supervisioná-lo cria um segundo caminho não supervisionado, e essa é frequentemente a razão mecânica pela qual visibilidade é restrita.
  3. Visibilidade corresponde ao escopo de corretude. A fronteira de visibilidade de um tipo é onde suas operações são completamente corretas, não meramente localmente válidas.

A coisa certa deve ser a única coisa.

Quando um tipo é dono de suas invariantes, estados inválidos são irrepresentáveis a nível de tipo. Quando a visibilidade corresponde ao escopo de corretude, interações inválidas são irrepresentáveis a nível de integração. A estrutura do código impede uso incorreto através da forma da API em si, em vez de depender de checks em runtime, avisos em documentação, ou disciplina de code review.

Trabalhos anteriores e o que há de novo aqui

Nada disso é novo, e o valor está em combinar conceitos estabelecidos em um único critério de decisão.

  • DDD Aggregates (Eric Evans, 2003) definem uma fronteira de consistência onde objetos externos mantêm referências apenas ao aggregate root e todas as mutações passam por ele. A relação folder/manager neste artigo é estruturalmente um aggregate. Mas Evans enquadra aggregates como uma diretriz de design (“direcione mutações pelo root”). Ele não conecta isso a modificadores de visibilidade como mecanismo de garantia em tempo de compilação, e não distingue entre leituras que são seguras em qualquer lugar e mutações que requerem o contexto do root. O princípio proposto aqui torna essa distinção explícita e permite que a linguagem a imponha.
  • Information Hiding (David Parnas, 1972) diz que cada módulo esconde uma “decisão de design” e define sua interface como “o conjunto de suposições que cada programador precisa fazer sobre o outro para demonstrar a corretude do seu próprio programa.” Isso é próximo em espírito, mas Parnas se preocupa em esconder detalhes de implementação (representações de dados, algoritmos). O princípio aqui é mais específico, dizendo quais operações esconder (as contextualmente incompletas) e por quê (elas requerem uma autoridade superior para corretude completa), em vez de esconder tudo atrás de uma interface uniforme.
  • Visibilidade assimétrica como mecanismo de linguagem existe desde Eiffel (Bertrand Meyer, 1986), onde selective export permite que cada feature especifique independentemente quais classes podem acessá-la. A sintaxe moderna de properties veio com C# 2.0 (2005) via public get; private set;, seguida por Swift (2014) com public private(set) var. Em Rust, a RFC 3323 (Restrictions) propõe pub mut(crate) para alcançar a mesma separação a nível de campo. Todos esses são mecanismos de visibilidade assimétrica de leitura/escrita. O princípio aqui fornece o raciocínio de design para quando e por que aplicar esses mecanismos, que é restringir a visibilidade de mutação quando a operação é localmente válida mas contextualmente incompleta.

A distinção entre operações localmente válidas e válidas a nível de sistema já está implícita em todos esses conceitos. A contribuição é um critério de decisão específico que diz que a fronteira de visibilidade de um tipo deveria ser onde suas operações são completamente corretas, não meramente localmente válidas. DDD diz “passe pelo root” mas não enquadra a autoridade do root em termos de completude contextual. Parnas diz “esconda decisões de design” mas não distingue leituras de mutações. As features de linguagem fornecem o mecanismo mas não o raciocínio. A síntese aqui nomeia uma pergunta específica (“essa operação é completamente correta aqui?”) e a conecta a uma ação específica (ajustar o modificador de visibilidade de acordo com a resposta).

Na prática

Ao decidir sobre visibilidade, pule o debate sobre confiança e pergunte em vez disso.

Essa operação é completamente correta aqui, ou é apenas localmente válida?

Se a operação é completamente correta isoladamente, torne-a public. Visibilidade restrita adiciona carga cognitiva, e você não deveria pagar esse custo sem uma razão. Se a operação é localmente válida mas contextualmente incompleta (um coordinator precisa disparar events, um service precisa recalcular estado derivado), restrinja a visibilidade à fronteira onde essa autoridade opera e deixe um comentário explicando por quê. Se você não consegue articular a invariante contextual que seria violada, a restrição é superproteção e deve ser removida.

Visibilidade indica onde a corretude vive, não é um mecanismo de segurança nem uma questão de confiança. Faça a coisa certa ser a única coisa.
